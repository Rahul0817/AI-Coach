# Oviora AI — Deployment Guide

Getting Oviora running locally, in staging and in production.

---

## Local development

### Option A — Docker (recommended)

```bash
git clone https://github.com/Rahul0817/AI-Coach.git
cd AI-Coach
cp .env.example .env
docker compose up --build
docker compose run --rm trainer   # ~30s; prediction endpoints 503 until this runs
```

| Service | URL |
|---|---|
| Frontend | <http://localhost:3000> |
| API docs | <http://localhost:8000/docs> |
| Health | <http://localhost:8000/health> |

The default `.env` needs no credentials. The stack runs on local fallbacks for
the LLM, embeddings and vector store.

### Option B — Native

```bash
# Postgres and Redis
docker compose up -d postgres redis

# Backend
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
python -m ml.train
alembic upgrade head
uvicorn app.main:app --reload

# Frontend
cd frontend && npm install && npm run dev
```

**System packages** the backend needs for OCR:

```bash
# Debian/Ubuntu
sudo apt-get install tesseract-ocr tesseract-ocr-eng poppler-utils
# macOS
brew install tesseract poppler
```

Without them the app still runs; scanned-report OCR returns a clear message
explaining what is missing.

## Configuration

Every setting is documented in [`.env.example`](../.env.example). The ones that
change behaviour most:

| Variable | Default | Effect |
|---|---|---|
| `ENVIRONMENT` | `development` | `production` enables strict boot checks and disables `/docs` |
| `SECRET_KEY` | random | **Must** be a strong value in production; the app refuses to boot otherwise |
| `LLM_PROVIDER` | `local` | `openai` for a real model; falls back with a warning if the key is missing |
| `EMBEDDING_PROVIDER` | `local` | `openai` for semantic retrieval |
| `RATE_LIMIT_REQUESTS` | `100` | Per identity, per window |
| `CHAT_RATE_LIMIT_REQUESTS` | `20` | Tighter budget for AI routes |
| `CLOUDINARY_*` | empty | Uploads go to local disk when unset |

### Production guardrails

The settings model **refuses to start** in production when:

- `SECRET_KEY` is a development default or shorter than 32 characters
- `DEBUG` is true
- `LLM_PROVIDER=openai` with no API key

This is deliberate. The most common way a project becomes a security incident
is shipping the sample signing key, and a loud failure at boot makes that
impossible.

Generate a key with:

```bash
python -c "import secrets; print(secrets.token_urlsafe(64))"
```

## Database migrations

```bash
cd backend

alembic upgrade head                              # apply
alembic revision --autogenerate -m "add x"        # create after model changes
alembic downgrade -1                              # roll back one
alembic upgrade head --sql > migration.sql        # offline SQL for a DBA
```

**Always review autogenerated migrations before committing.** Alembic detects
most changes but cannot infer intent — a renamed column looks identical to a
drop plus an add, which would lose data.

CI fails the build if models change without a matching migration.

## Production deployment

### 1. Provision

- **PostgreSQL 16+** with automated backups and PITR
- **Redis 7+** with `maxmemory-policy allkeys-lru`
- Container runtime (ECS, Cloud Run, Kubernetes, Fly.io)
- Object storage for uploads (Cloudinary or S3)

### 2. Build

```bash
docker build -t oviora-api:$(git rev-parse --short HEAD) ./backend
docker build -t oviora-web:$(git rev-parse --short HEAD) \
  --build-arg NEXT_PUBLIC_API_URL=https://api.yourdomain.com ./frontend
```

`NEXT_PUBLIC_*` values are inlined at build time, not read at runtime — the
API URL must be a build argument.

### 3. Migrate, then deploy

Run migrations as a separate job *before* rolling out new application
containers. Running them from an app container's entrypoint means N replicas
racing the same migration.

```bash
docker run --rm -e DATABASE_URL=$DATABASE_URL oviora-api:TAG alembic upgrade head
```

### 4. Train the model

```bash
docker run --rm -v model-artifacts:/app/ml/artifacts oviora-api:TAG python -m ml.train
```

Mount the artifact volume read-only into the API containers. Prediction
endpoints return 503 without it; everything else works.

### 5. Health checks

| Endpoint | Use | Behaviour |
|---|---|---|
| `/health/live` | Liveness probe | No dependencies touched — a database blip must not kill a healthy pod |
| `/health/ready` | Readiness probe | 503 when a dependency is down, so the load balancer stops routing |
| `/health` | Operator dashboard | Full status including which fallbacks are active |

### 6. Scaling

**One uvicorn worker per container.** The ML model and knowledge base load per
process, so multiple workers multiply the memory footprint inside a single
limit. Scale by adding containers.

| Load | Suggested shape |
|---|---|
| < 1k users | 2 API containers, 1 web, shared small Postgres |
| 1k–10k | 4 API, 2 web, Postgres with a read replica, dedicated Redis |
| 10k+ | Autoscaling, pgvector instead of embedded Chroma, materialised dashboard aggregates |

## Observability

Logs are JSON in production, one object per line, with `request_id` and
`user_id` on every entry — including lines written deep inside the agent layer,
which never sees the HTTP request.

Worth alerting on:

| Signal | Why |
|---|---|
| `rate limit exceeded` spikes | Abuse, or a limit that is too tight |
| `crisis language detected` | Not an error — but worth knowing the volume |
| `shap explanation failed` | Explanations silently degraded to the fallback |
| `redis unavailable` | Rate limiting is no longer shared across workers |
| `model artifact not found` | Prediction endpoints are down |
| p95 latency on `/api/v1/chat` | The main user-visible performance signal |

## Backup and recovery

**Postgres is the only stateful component that matters.** Redis holds
reconstructible data. The vector index rebuilds from the knowledge base in
seconds. The model artifact is regenerated by re-running training.

```bash
pg_dump -Fc $DATABASE_URL > oviora-$(date +%F).dump    # backup
pg_restore -d $DATABASE_URL --clean oviora-2026-01-15.dump   # restore
```

Test restores on a schedule. An untested backup is a hypothesis.

## Troubleshooting

**Prediction endpoints return 503**
The model artifact is missing. Run `python -m ml.train` and restart.

**Chat answers are quoted rather than conversational**
`LLM_PROVIDER=local`. That is the extractive fallback working as designed. Set
`LLM_PROVIDER=openai` with a key for generated prose.

**`MissingGreenlet` on a write endpoint**
An ORM attribute is being read after it was expired by a server-side default.
`Base.__mapper_args__ = {"eager_defaults": True}` handles the existing cases;
a new one usually means an implicit lazy load somewhere in an async path.

**Scanned PDFs fail to parse**
Tesseract or Poppler is missing. The API says which. Digital PDFs still work,
since they use the text layer rather than OCR.

**CORS errors in the browser**
`BACKEND_CORS_ORIGINS` must list the frontend origin exactly, including scheme
and port. Wildcards are rejected because credentials are enabled.

**Rate limits behaving oddly across replicas**
Redis is unreachable and each container is counting independently in memory.
Check `/health`.
